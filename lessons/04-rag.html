什么是 RAG？

RAG（Retrieval-Augmented Generation）解决 LLM 的两个根本缺陷：

LLM 的缺陷 没有 RAG 有 RAG
幻觉 编造不存在的政策、数据、事实 所有回答基于检索到的真实文档
知识截止 不知道训练截止日期之后的内容 搜索最新文档，实时获取新知识
私有知识盲区 不知道你的公司政策、产品文档 读取你的专属文档并给出精确答案
RAG = 检索 + 生成。先搜到相关文档，再把文档内容塞进 prompt，让 LLM 基于这些内容回答。本质上就是"开卷考试"。

经典 Chain RAG vs Agent RAG

范式 1: 经典 Chain（老方式）

// 固定管道: embed → store → retrieve → generate
const chain = createRetrievalChain({ retriever, llm });

范式 2: Agent RAG（✅ 你学的方式）

// 检索就是一个 tool — Agent 自主决定何时搜索、搜什么
const searchKB = tool(
  ({ query }) => { /* 搜索逻辑 */ },
  { name: "search_knowledge_base" }
);
const agent = createAgent({ model, tools: [searchKB] });
为什么 Agent RAG 更好？Agent 可以自主决定：是否需要搜索、搜索什么关键词、搜不到时要不要换关键词重搜、结果不足时要不要追问用户。固定 Chain 做不到这些。

三种检索策略

策略 原理 适合
关键词匹配 分词 → 统计匹配次数 → 排序 小规模（<1000 篇）、主题集中
向量语义搜索 文本 → Embedding → 余弦相似度 → Top-K 大规模、需要语义理解
混合搜索 关键词 + 向量双路检索 → 融合排序 生产环境最佳实践

防幻觉：System Prompt 约束

{
  role: "system",
  content:
    "所有答案必须基于知识库搜索结果，不要编造。" +
    "如果搜索结果中没有相关信息，诚实告知。"
}

你的 04-rag-demo.ts 第四个问题（"公司有健身房吗？"）正好验证了这一点——Agent 诚实地说"找不到"。

动手实践

你已经在 04-rag-demo.ts 中添加了第 7 条文档（健康福利政策）。重新跑 npx tsx 04-rag-demo.ts，再问一遍"健身房"——这次 Agent 能找到企业合作的 SuperFit 健身房了。

这就是 RAG 的核心价值：更新知识库 = 更新 Agent 的知识。不用重新训练模型，只加一条文档，Agent 就能回答新问题。

知识检查

1. Agent RAG 相比经典 Chain RAG 的核心优势是什么？
A. 搜索速度更快，因为使用了更高效的索引结构
B. Agent 能自主决定是否搜索、搜什么、搜不到时怎么调整策略
C. 向量搜索的精度更高，因为 Agent 可以压缩 embedding 维度
D. 不需要文档预处理，可以直接搜索任意格式的文件
2. 为什么 system prompt 中要加"如果搜索无结果，诚实告知"？
A. 让 Agent 的回复看起来更礼貌、更专业
B. 防止 Agent 在检索无结果时凭模型自身知识编造答案（幻觉）
C. 减少 API 调用次数，节省 token 成本
D. 让 Agent 自动触发知识库的重新索引
3. 从关键词搜索升级到向量语义搜索，解决了什么根本问题？
A. 搜索速度 — 向量搜索比字符串匹配快 10 倍以上
B. 语义理解 — "远程工作" 和 "work from home" 能匹配到同一篇文档
C. 存储空间 — 向量压缩后文档占用空间减少 90%
D. API 成本 — embedding API 比关键词搜索 API 便宜
