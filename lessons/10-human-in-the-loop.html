Lesson 10: Human-in-the-loop — interrupt + Command

📅 2026-07-17 ⏱ ~25 分钟 🎯 在 LangGraph 工作流中插入人工审批点，暂停等待并恢复执行 📎 课前要求: Lesson 08 LangGraph Agent

你将要学会的

  1. interrupt() — 在图节点中挂起执行，等待人工输入
  2. Command({ resume }) — 恢复被挂起的图，传入人工决策
  3. MemorySaver + thread_id — 跨 invoke 持久化图状态
  4. 审批工作流模式 — LLM 提方案 → 人审批 → 执行

问题：Agent 不应该能自己做所有决定

前九课构建的 Agent 和 Graph 都是全自动的——给了输入，一路跑到输出。但在生产环境中：

  • 大额转账需要人工审批
  • 代码部署需要技术主管确认
  • 内容发布需要编辑审核

这些场景中，你不能让 Agent 自己决定「批准」——需要插入一个人工关卡。

Human-in-the-loop 就是解决这个问题的。LangGraph 提供了 interrupt() 在任意节点中挂起图，然后用 Command({ resume }) 恢复。图的状态通过 checkpointer 持久化，所以「审批者」可以是几分钟后的另一次 API 调用。

先跑代码

cd learn-langchain
npx tsx 10-human-in-the-loop.ts

观察每个演示中的「invoke 1(挂起) → invoke 2(恢复)」模式。

核心 API

API 作用 示例
interrupt(msg) 在节点中挂起图 const result = interrupt("请审批")
Command({ resume }) 恢复执行，传入值给 interrupt() new Command({ resume: "approve" })
MemorySaver 内存 checkpointer，持久化图状态 .compile({ checkpointer: new MemorySaver() })
thread_id 线程 ID，关联多次 invoke { configurable: { thread_id: "xxx" } }

演示 1: 基础审批关

// 图中有一个人工审批节点
.addNode("review", (_state) => {
  // interrupt() 挂起图，返回值给调用方
  const decision = interrupt({
    question: "请审核此操作",
    options: ["approve", "deny"],
  });
  return { decision };
})

// 第一次 invoke: 运行到 interrupt，挂起
const r1 = await graph.invoke({ messages: [...] }, config);
// → 图暂停，r1 是挂起前的状态

// 第二次 invoke: 用 Command 恢复，传入审批结果
const r2 = await graph.invoke(
  new Command({ resume: "approve" }),  // ← interrupt() 返回 "approve"
  config  // ← 相同 thread_id，继续之前的图
);
// → 图从 interrupt 之后继续执行
关键是 thread_id。同一个 thread_id 的多次 invoke 共享同一个图状态。第一次 invoke 在 interrupt 处挂起，第二次 invoke 从那里继续。不同 thread_id → 不同的图实例。

演示 2: LLM 建议 + 人工审批

START → analyze (LLM分析+提方案) → ⏸️ approval (人工审批) → execute → END
                                                   └→ deny → END

这是生产中最常见的模式：

  1. LLM 分析: Agent 分析问题，提出具体方案，但不执行
  2. 人工审批: interrupt() 挂起，人类审查方案
  3. 执行 or 拒绝: 根据审批结果走不同分支

演示 3: 多步工单流程

分类 → ⏸️ 技术审批 → 修复 → 关闭 → END

工单处理流程演示了 Checkpoints 的价值——每个步骤之后图状态都被持久化，即使服务重启也能从中断点继续。

执行模式图解


invoke 1:  START → triage → ⏸️ interrupt (挂起)
                              │
              返回挂起状态给调用方
                              │
invoke 2:                  Command({resume: "approve"})
                              │
                           fix → close → END ✅

生产环境注意事项

注意点 说明
Checkpointer 选择 MemorySaver 只适合开发/测试。生产环境用 PostgresSaver 或 SqliteSaver
interrupt 的返回值类型 可以是字符串（简单审批）、对象（多字段表单）、甚至文件
超时处理 挂起状态不会自动超时。需要在应用层实现超时逻辑（定时检查 + 自动拒绝/升级）

知识检查

1. interrupt() 在图节点的内部做了什么？
A. 抛出一个异常，让调用方捕获
B. 返回一个特殊值给调用方，下次 invoke 时从同一位置继续执行
C. 休眠当前线程，等待 setTimeout 触发
D. 将当前节点标记为「待定」，让下一个节点处理
2. 为什么需要 MemorySaver checkpointer？
A. 它是 interrupt 能工作的前提——图状态需要被持久化才能跨 invoke 恢复
B. 它是 LangGraph v2 的强制要求，不传会编译失败
C. 它提供内存优化，减少 token 消耗
D. 它是 DeepSeek API 的兼容性补丁
3. 一个 thread_id 关联了两次 invoke，第二次用 Command 恢复后，图从哪里开始执行？
A. 从 START 重新执行整个图
B. 从 interrupt() 调用的下一行代码继续，interrupt() 返回 Command 中的 resume 值
C. 跳过 interrupt 所在的节点，直接从下一个节点开始
D. 从最后一个 executed 节点重新执行
