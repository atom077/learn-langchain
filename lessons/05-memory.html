Lesson 05: Memory — 对话记忆与多轮交互

问题：Agent 天生是"失忆症患者"

你在前面四课中写的所有 Agent，每次 invoke() 都是独立的全新对话。看演示 1：

// 第 1 轮
const r1 = await agent.invoke({
  messages: [
    { role: "system", content: "你是助手。" },
    { role: "user", content: "我叫小明。" },
  ],
});
// → Agent: "记住了，小明！"

// 第 2 轮 — 没有传入第 1 轮的消息！
const r2 = await agent.invoke({
  messages: [
    { role: "system", content: "你是助手。" },
    { role: "user", content: "我叫什么名字？" },
  ],
});
// → Agent: "我们还没认识呢，你叫什么？"  ← 失忆了！
Agent 没有内置记忆。每次 invoke() 都是一个全新的 LLM 请求。Agent 只能看到你在 messages 数组里传入的内容——如果历史消息不在数组里，Agent 就不知道。

解决方案 1: 手动记忆（最直接）

把消息数组维护在外部变量中，每次 invoke 后追加 AI 回复，下次 invoke 时传入完整历史：

// 维护一个外部消息历史
let history = [
  { role: "system", content: "你是助手。用中文回复。" },
];

// 第 1 轮
history.push({ role: "user", content: "我叫小明。" });
const r1 = await agent.invoke({ messages: [...history] });
history.push({ role: "assistant", content: lastContent(r1) });

// 第 2 轮 — 传入完整历史
history.push({ role: "user", content: "我叫什么名字？" });
const r2 = await agent.invoke({ messages: [...history] });
// → "你叫小明。"  ← 记得了！

这就是 Conversation Buffer Memory——把整个对话历史当作记忆。简单、可靠，但消息越多 token 消耗越大。

解决方案 2: 窗口记忆（控制成本）

当对话很长时，完整历史会超出上下文窗口或消耗大量 token。解决方案：只保留最近 N 条消息。

const WINDOW_SIZE = 5; // system(1) + 最近 4 条

function windowTruncate(history, size) {
  const systemMsg = history[0];           // 始终保留 system prompt
  const recent = history.slice(-(size - 1)); // 最近的消息
  return [systemMsg, ...recent];
}

// 长对话 → 截断后只有最近 5 条
const truncated = windowTruncate(longHistory, WINDOW_SIZE);
const result = await agent.invoke({
  messages: [...truncated, { role: "user", content: "记得我叫什么吗？" }],
});
// → "抱歉，我不知道你的名字。"  ← 早期信息被截掉了！
权衡：窗口记忆用遗忘换成本。窗口越小越省钱，但 Agent 能记住的上下文越少。适合"只需要最近几轮上下文"的场景（如客服对话中只需要记得当前问题的相关细节）。

解决方案 3: 摘要记忆（平衡方案）

把被窗口截掉的早期对话压缩成一段摘要，注入 system prompt。这样既节省 token，又不完全丢失早期信息：

// 把早期对话压缩为摘要
const earlySummary =
  "[对话摘要] 用户叫小明，喜欢看电影（尤其是科幻片）和打篮球。";

const result = await agent.invoke({
  messages: [
    {
      role: "system",
      content: `你是助手。${earlySummary}`,  // 摘要注入 system prompt
    },
    ...recentMessages,
    { role: "user", content: "推荐一部适合我的电影。" },
  ],
});
// → "推荐《头号玩家》——科幻题材，节奏紧凑适合爱运动的人。"
// ✅ 虽然早期消息被截掉了，但 Agent 通过摘要知道了用户偏好！

摘要可以由另一个 LLM 调用来生成，或者在你自己的业务逻辑中维护。

三种策略对比

策略 记忆完整度 Token 成本 适合场景
Buffer 100% 线性增长，无上限 短对话、原型、测试
Window 最近 N 条 固定上限 客服、需要最近上下文的场景
Summary 压缩但不丢失关键信息 摘要 + 窗口 长期对话、个人助手

总结：Memory 不是什么神秘的东西

LangChain.js 的 Agent API 中，Memory 不是框架内置的黑盒——它就是你对消息历史的管理策略：

  1. 维护一个消息数组
  2. 每次 invoke() 时传入
  3. 每次返回后追加 AI 回复
  4. 根据需要截断、压缩、或存储
你已经有能力构建一个完整的聊天应用了：RAG 工具让 Agent 能搜索知识库，Memory 让它能记住对话历史，Tool 让它能执行操作。这三者的组合就是你简历上那个"构建过生产级 AI Agent"的证明。

知识检查

1. Agent 为什么会在两次 invoke 之间"失忆"？
A. Agent 的模型权重在每次调用后被重置
B. 每次 invoke 是独立的请求，Agent 只能看到传入的 messages 数组
C. LangChain.js 会自动清除 Agent 的内部状态缓存
D. DeepSeek 的 API 不支持多轮对话
2. 窗口记忆（Window Memory）的主要代价是什么？
A. 代码复杂度大幅增加，需要引入额外的数据库
B. 窗口外的早期信息被丢弃，Agent 可能忘记重要的上下文
C. 每次调用需要额外的 API 请求来压缩历史
D. 只能处理英文对话，不支持中文
3. 摘要记忆 + 窗口记忆的组合方案解决了什么问题？
A. 完全消除了 token 消耗，让对话零成本运行
B. 在控制 token 成本的同时，通过摘要保留早期关键信息
C. 让 Agent 能同时处理 100 个并发对话
D. 将对话历史的存储从内存迁移到 GPU 显存
