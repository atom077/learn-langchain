Lesson 13: 现代 Agent Harness 与 Middleware

2026-09-22 约 20 分钟 目标：掌握 Agent loop 的扩展边界 前置：Lesson 01、Lesson 12

本课的一个胜利

你会写出一个 Middleware，让 Agent 在每次模型调用前自动记录次数，并把本次请求的用户上下文注入 system message。这个能力是重试、限流、路由、审计、PII 检测和动态提示词的共同基础。

官方当前心智模型：Agent = Model + Harness。模型负责“下一步生成什么”，harness 负责“给它什么上下文、哪些工具，以及调用前后允许插入什么控制逻辑”。官方 Overview

先看 Agent loop

invoke(input, context)
  │
  ├─ beforeAgent       一次：初始化或校验
  ├─ beforeModel       每次模型调用前
  ├─ wrapModelCall     包住模型调用
  ├─ model             返回回答或 tool_calls
  ├─ afterModel        每次模型调用后
  ├─ tools             如果有工具调用，执行后再次回到模型
  └─ afterAgent        一次：收尾

模型第一次返回 tool_calls 时，Agent 不会结束，而是执行工具，再把工具结果送回模型。因此“每次模型调用”可能发生多次；这正是 beforeModel 与 wrapModelCall 的区别重点。

两种 Middleware hook

类型 Hook 最适合
Node-style beforeAgent、beforeModel、afterModel、afterAgent 校验、日志、状态更新
Wrap-style wrapModelCall、wrapToolCall 修改请求、重试、回退、鉴权、缓存

Node-style hook 直接返回 state 更新；Wrap-style hook 拿到 request 与 handler，决定是否以及如何继续调用下一个环节。当前官方文档把 Middleware 描述为控制 Agent 执行的扩展机制，详见 Middleware overview 和 Custom middleware。

State 与 Context：不要混用

state   = Agent 执行中产生的状态，可由 checkpointer 跨调用保存
context = 本次 invoke 的只读元数据，不会自动持久化

state:   messages, modelCallCount, workflowStep
context: userId, tenantId, locale, requestId

在 Middleware 中，状态从 state 读取；运行时上下文从 runtime.context 读取。一个实用判断是：如果下一次调用还必须知道它，它更像 state；如果只是本次请求的身份、权限或配置，它更像 context。

动手：离线运行实验

npm run demo:13

实验使用 LangChain 当前测试工具里的 fakeModel()，不访问模型 Provider。它会模拟“两次模型调用”：第一次请求工具，第二次生成最终回答。你应该看到：

[beforeModel] call=1 ...
[wrapModelCall] 已注入本次 invoke 的 context
[afterModel] last=ai
[beforeModel] call=2 ...
[wrapModelCall] 已注入本次 invoke 的 context
[afterModel] last=ai

[result] modelCallCount=2

打开 13-middleware-demo.ts，定位三个地方：

  1. beforeModel 把 modelCallCount 写回 state。
  2. wrapModelCall 用 runtime.context 改写本次模型请求。
  3. fakeModel 的两次响应证明工具调用会让 Agent 回到模型循环。
