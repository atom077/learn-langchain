你将要构建的

一个交互式命令行个人 AI 助手——它能搜索你的知识库、帮你记笔记、做计算， 并且在多轮对话中记住你的上下文。这不是玩具项目，而是你在前五课学到的每一项技能的综合应用。

为什么这个项目值得展示？它在一个应用中集成了 Agent 开发的三个核心能力——RAG（知识检索）、Memory（对话记忆）、Tools（工具调用），外加流式输出和交互式 CLI。这正是你在面试中要展示的「从零构建生产级 AI Agent」的项目作品。

核心设计决策

1. Memory: Summary + Window 混合

这不仅是 Lesson 05 的"手动消息数组"，而是自动压缩的生产级方案：

const WINDOW_SIZE = 6;             // 保留最近 6 条消息
const SUMMARIZE_THRESHOLD = 10;    // 超过 10 条时触发压缩

async function compressHistory() {
  if (history.length <= SUMMARIZE_THRESHOLD) return;

  const earlyMsgs = history.slice(0, -(WINDOW_SIZE - 1));
  const recentMsgs = history.slice(-(WINDOW_SIZE - 1));

  // 用 LLM 自动生成摘要
  const compressResult = await model.invoke([...]);
  summary = `[对话背景] ${compressResult.content}`;

  history = recentMsgs; // 只保留最近的消息
}
为什么不用手动摘要？你自己写的摘要规则永远无法像 LLM 那样理解对话的语义重点——"小明计划离职"比"小明喜欢吃披萨"更需要被记住。让 LLM 决定保留什么，这才是 Agent 时代的方式。

2. RAG: Tool-based Agent RAG

检索不是独立的 pipeline——它是 Agent 的一个工具。Agent 自己决定什么时候搜、搜什么、搜不到怎么办：

const searchNotes = tool(
  ({ query }) => { /* TF-like 关键词匹配 + 标签加权 */ },
  {
    name: "search_notes",
    description:
      "搜索个人知识库中的笔记。当用户询问任何关于项目、会议、" +
      "学习记录、职业规划、健身计划等信息时，必须先搜索知识库。",
    schema: z.object({
      query: z.string().describe("搜索关键词"),
    }),
  }
);

完整的数据流

从一个用户消息到 AI 回复的完整路径：

  1. 用户输入 → readline 捕获
  2. Memory 组装 → 系统提示词 + 摘要 + 最近 N 条历史 + 当前消息 → messages[]
  3. Agent 推理 → ReAct 循环：思考是否需要工具 → 需要则调用 → 观察结果 → 继续推理
  4. 流式输出 → 实时展示每个 chunk（思考/工具调用/最终回复）
  5. 历史更新 → AI 回复追加到 history[]
  6. 自动压缩 → 历史超过阈值 → LLM 摘要 → 重置为摘要 + 最近消息
这就是 Agent 应用的完整生命周期。理解了这六个步骤，你就理解了 80% 的生产级 Agent 系统是如何工作的。其他一切——向量数据库、LangSmith、LangGraph——都是在这个骨架上添加的优化。

扩展方向（面试加分项）

如果你想让这个项目更「生产级」，可以考虑这些扩展：

  1. 持久化存储 — 用 SQLite 或文件系统替代内存数组，重启不丢数据
  2. 真正的向量搜索 — 用 @langchain/community 的 VectorStore 替代 TF 关键词匹配
  3. LangSmith 追踪 — 加 LANGSMITH_API_KEY 环境变量，可视化每一步推理
  4. 多 Agent 协作 — 用 LangGraph 拆成「检索 Agent」「笔记 Agent」「通用 Agent」
  5. Web UI — 用 Next.js + Vercel AI SDK 替代 CLI，做成真正可部署的聊天应用

知识检查

1. 这个项目的 Memory 为什么选用 Summary + Window 混合策略，而不是单纯的 Buffer？
A. Buffer Memory 在 LangChain.js v1 中已被废弃，无法使用
B. 单纯 Buffer 在长对话中 token 成本线性增长无上限，混合策略用摘要控制成本同时保留关键信息
C. DeepSeek 的 API 不支持超过 100 条消息的请求
D. Summary + Window 是 LangChain.js 框架强制要求的模式
2. 为什么把 RAG 检索做成 Agent 的一个 tool，而不是独立的 pipeline？
A. tool 形式的 RAG 让 Agent 自己决定何时搜索、搜什么、搜不到时如何调整，比固定 pipeline 更灵活
B. pipeline 方式需要额外的数据库连接，tool 方式不需要
C. LangChain.js v1 只支持 tool，不支持 pipeline
D. tool 方式的检索速度比 pipeline 快 10 倍以上
3. `compressHistory()` 中为什么用 LLM 来生成摘要，而不是写规则（比如只保留包含特定关键词的消息）？
A. 规则方式需要写更多代码，而 LLM 方式代码更短
B. LLM 能理解对话的语义重要性——「用户计划离职」比「用户喜欢吃披萨」更值得被记住——这是规则做不到的
C. DeepSeek 的摘要 API 是免费的，不会增加额外成本
D. 规则方式会触发 TypeScript 编译器的严格模式警告
